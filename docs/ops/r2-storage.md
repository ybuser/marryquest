# Cloudflare R2 timeline storage runbook

## Scope and current state

Recovery-03 replaces the Netlify Function multipart upload with a two-bucket, browser-direct R2 flow. The repository now contains the storage provider, presign/finalize APIs, image validation, readiness check, and upload rate-limit declaration. It does not create or configure Cloudflare or Netlify resources.

At the time of this change:

- The existing Netlify staging deployment, `/api/health`, protected `/api/ready`, and owner login were validated before the R2 change.
- No R2 staging bucket or API token has been created by this change.
- The R2 custom domain has not been connected.
- Netlify does not yet have the R2 variables.
- No upload has been sent to Cloudflare R2 and no post-merge Netlify upload smoke has run.
- Production Neon, production R2 resources, the production domain, and a production release remain unprovisioned and unapproved.

The recovered Supabase backup and Storage objects are not imported. Do not restore old Supabase credentials as a fallback.

## Two-bucket architecture

Use two distinct Standard-storage buckets:

| Boundary | Staging name | Access | Object prefix |
| --- | --- | --- | --- |
| Temporary originals | `marryquest-upload-staging` | Private only | `tmp/timeline/` |
| Validated assets | `marryquest-assets-staging` | Public through the custom domain | `timeline/` |

The authenticated browser requests a five-minute presigned PUT, sends the original directly to the private bucket, and sends only a small JSON finalize request to Next.js. The server checks the stored size and content type, reads at most 10 MiB through a bounded stream, decodes the actual image with Sharp, and writes a metadata-free 640×640 WebP to the public bucket.

The application never gives an R2 access key to browser code. A presigned URL is a short-lived bearer token: do not log it, persist it, or include it in tickets or screenshots.

## Object and image policy

- Temporary keys are generated by the server as `tmp/timeline/{userId}/{invitationId}/{cardId}/{uploadId}`.
- Final keys are deterministically derived as `timeline/{invitationId}/{cardId}-{uploadId}.webp`.
- Every ID segment must match `^[A-Za-z0-9_-]{1,128}$`; invalid input is rejected, not sanitized.
- `uploadId` is a server-generated UUID. A caller cannot supply an arbitrary object key or filename.
- Input MIME is limited to JPEG, PNG, or WebP and the actual decoded format must match the stored MIME.
- Actual stored size must be 1 byte through 10 MiB.
- Sharp uses an explicit 80-megapixel input limit. This admits common 48/50-megapixel phone photos while rejecting unusually large decoded inputs well below Sharp's much broader default.
- Processing is `rotate` → 640×640 `cover` with `attention` positioning → WebP quality 82.
- The pipeline does not call `withMetadata` or `keepMetadata`; EXIF, GPS, ICC, and XMP metadata are not retained.
- Output must be WebP, exactly 640×640, and no larger than 2 MiB before public PUT.
- Public objects use `Content-Type: image/webp` and `Cache-Control: public, max-age=31536000, immutable`.

Finalize is idempotent. The deterministic final key means a repeated request returns the same URL and does not create another object. A successful final PUT is followed by best-effort temp deletion. Invalid images are also deleted best-effort. If the public PUT has a transient failure, the valid temp object is deliberately retained for retry and the one-day lifecycle is the bounded fallback.

## Staging resource setup

This is manual Cloudflare Dashboard work after the Recovery-03 PR is merged and explicitly approved.

Recommended staging resources:

- Private upload bucket: `marryquest-upload-staging`
- Public asset bucket: `marryquest-assets-staging`
- Public custom domain: `assets-staging.marryquest.shimyunbo.com`

For both buckets:

- Select Standard storage.
- Keep the automatic/default location.
- Do not enable Infrequent Access.

For the private upload bucket:

1. Keep public development URL access disabled.
2. Do not attach a custom domain.
3. Add a one-day lifecycle deletion rule scoped to `tmp/` (or the whole bucket if it is dedicated to temporary uploads).
4. Remember that lifecycle deletion is asynchronous and can occur after the nominal expiration time.
5. Configure the exact browser PUT CORS policy below.

For the public asset bucket:

1. Connect `assets-staging.marryquest.shimyunbo.com`.
2. Allow public reads only for the finalized WebP assets.
3. Disable the `r2.dev` public development URL after the custom domain is active; these access modes are independent.
4. Use a minimum TLS version of 1.2 for the custom domain.

See Cloudflare's [public bucket](https://developers.cloudflare.com/r2/buckets/public-buckets/) and [lifecycle](https://developers.cloudflare.com/r2/buckets/object-lifecycles/) documentation while applying these settings.

## Bucket-scoped API token

Create one staging-only R2 API token with Object Read & Write access restricted to the two staging buckets. Do not grant account-wide Administrator access and do not reuse this token for production.

Cloudflare displays the Access Key ID and Secret Access Key during creation; the secret cannot be retrieved later. Move both directly into the approved secret store. Never paste them into source, a PR, a deploy log, a shell transcript, or a `NEXT_PUBLIC_*` variable. See Cloudflare's [R2 token documentation](https://developers.cloudflare.com/r2/api/tokens/).

## Private-bucket CORS

For the stable staging site, start with this exact policy:

```json
[
  {
    "AllowedOrigins": ["https://marryquest.netlify.app"],
    "AllowedMethods": ["PUT"],
    "AllowedHeaders": ["Content-Type"],
    "ExposeHeaders": ["ETag"],
    "MaxAgeSeconds": 3600
  }
]
```

The origin has no trailing slash or path. Do not use `*`. The implementation signs and sends only `Content-Type`; if that contract changes, update the presign response, browser request, and CORS `AllowedHeaders` together. Presigned URLs do not bypass browser CORS. Refer to Cloudflare's [presigned URL](https://developers.cloudflare.com/r2/api/s3/presigned-urls/) and [CORS](https://developers.cloudflare.com/r2/buckets/cors/) guidance.

## Server-only environment variables

Configure these values only in the Netlify stable staging `Production` deploy context after the Cloudflare resources exist:

- `R2_ACCOUNT_ID`
- `R2_ACCESS_KEY_ID`
- `R2_SECRET_ACCESS_KEY`
- `R2_ENDPOINT`
- `R2_UPLOAD_BUCKET`
- `R2_PUBLIC_BUCKET`
- `R2_PUBLIC_BASE_URL`

The S3 client uses region `auto`, the explicit R2 endpoint, and server-only credentials. Production configuration requires HTTPS, distinct valid bucket names, and a public base URL without credentials, query, or fragment. Local development/test permits an HTTP loopback MinIO endpoint and uses path-style requests.

Mark the access key and secret as containing secret values. Keep all actual R2 values out of Deploy Preview, branch deploy, local-development, and all-deploy contexts. See `netlify-staging.md` for the public-repository context policy and fail-closed preview placeholders.

## Readiness and post-merge staging gate

Protected `/api/ready` now requires all of the following:

- valid application and owner configuration;
- a successful PostgreSQL readiness query;
- `HeadBucket` success for the private upload bucket;
- `HeadBucket` success for the public asset bucket.

Failure remains `503 {"status":"not_ready"}` and does not expose credentials, endpoint, bucket, or SDK error details.

After setting the approved staging variables and deploying the exact merged commit:

1. Confirm deploy post-processing accepts both code-based rate-limit rules.
2. Confirm missing/wrong admin passphrases still return 401 from `/api/ready`.
3. Confirm the correct passphrase returns 200 only when the DB and both buckets are ready.
4. Sign in as the configured owner on the stable staging URL.
5. Upload JPEG, PNG, and WebP timeline photos and confirm the browser sends JSON to presign, binary directly to R2, and JSON to finalize.
6. Confirm the public URL uses the staging asset domain and the object is a 640×640 WebP.
7. Save the Timeline tab, reload the Builder, and open the public invitation.
8. Remove a saved photo, save again, and confirm only the recognized old staging object is deleted.
9. Perform a controlled upload-rate test and confirm requests above 20 POSTs in 60 seconds receive 429. Local testing is not evidence that Netlify accepted this rule.
10. Inspect deploy and Function logs for accidental presigned URL, endpoint, bucket, or credential disclosure.

Do not run Prisma migration commands, seed commands, or R2 administration from a Netlify build or Function.

## Saved-asset cleanup and known limitations

Timeline save takes the old photo URL snapshot before its existing DB transaction. After a successful transaction, cleanup first confirms that the transaction's card IDs still match the current saved revision, then checks that each candidate URL has zero current `TimelineCard` references before deleting it. It deletes only removed URLs that exactly match the configured public origin and `timeline/{invitationId}/` final-key format. External URLs, legacy Supabase URLs, malformed URLs, and another invitation's prefix are ignored. Cleanup failure or a newer concurrent revision is logged with a fixed code and never rolls back or fails the DB save. PostgreSQL and R2 do not share a transaction, so this remains best-effort and later orphan reconciliation is still required.

Recovery-03 does not fully collect:

- a finalized asset when the owner closes the browser before saving the Timeline tab;
- all assets when an invitation is soft-deleted;
- Gallery assets.

Use lifecycle/usage monitoring now. Add an approved orphan-reconciliation job and invitation-delete/Gallery cleanup in a later Recovery step; do not broadly delete public objects without comparing them with stored DB URLs.

## Production separation

Production must use separate resources and credentials:

- Private bucket: `marryquest-upload`
- Public bucket: `marryquest-assets`
- Public domain: `assets.marryquest.shimyunbo.com`
- Separate bucket-scoped production API token

Do not reuse staging buckets, keys, token, or custom domain. This runbook does not approve production provisioning or migration.

## Cost and monitoring

Cloudflare's R2 free tier applies to Standard storage, not Infrequent Access. Review the current [R2 pricing](https://developers.cloudflare.com/r2/pricing/) before provisioning. The temp lifecycle limits storage growth, but also monitor object count, stored bytes, and Class A/B operations. Configure usage notifications and a budget alert. A budget alert is notification and visibility, not a hard spending cap.

## Rollback

- Revert the PR or roll back to the previous known-good Netlify deploy for a code regression.
- Do not restore Supabase credentials or reactivate the old multipart Function route as an operational fallback.
- Correct R2 credentials/configuration in the secret store and redeploy when readiness fails.
- Do not bulk-delete public objects until Timeline database URLs and object inventory have been compared.
- Retire staging buckets only after upload smoke has stopped and stored staging URLs have been removed or intentionally abandoned.
- No Prisma schema or database migration rollback is part of Recovery-03.
