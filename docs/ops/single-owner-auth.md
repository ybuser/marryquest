# Single-owner authentication runbook

## Architecture and security boundary

MarryQuest uses one operator identity configured through server-side environment variables. There is no public signup flow, demo account, fixed development fallback, or repository-stored password. The Credentials provider verifies the configured owner and upserts one Prisma `User` only after both credential checks succeed.

Owner and security variables (all are required except `OWNER_NAME`):

- `OWNER_LOGIN_ID`: the case-insensitive login identifier. It is never sent to the client as configuration.
- `OWNER_EMAIL`: the stable Prisma `User.email` identity used by the owner upsert.
- `OWNER_NAME`: the optional display name.
- `OWNER_PASSWORD_HASH`: the versioned scrypt hash generated by the repository script. It is not a plaintext password, but it is still sensitive configuration and belongs in the approved secret store.
- `NEXTAUTH_SECRET`: the NextAuth signing secret.
- `QUIZ_BADGE_SECRET`: the independent quiz-badge signing secret.
- `ADMIN_PASSPHRASE`: the independent credential for protected readiness and the admin statistics route.

Never prefix these variables with `NEXT_PUBLIC_`. Generate separate staging and production values, and never reuse one value for `NEXTAUTH_SECRET`, `QUIZ_BADGE_SECRET`, or `ADMIN_PASSPHRASE`.

The public `replace-with-*` strings in `.env.example` are deliberately rejected by authentication, quiz signing, admin-passphrase verification, and readiness checks. They are labels, not development fallbacks. An invalid or missing `NEXTAUTH_SECRET` is never used as a JWT key; the process substitutes a non-persisted random fail-closed key while owner authorization remains disabled and readiness returns `503`.

## Stable owner identity

`OWNER_EMAIL` is the Prisma identity key, not merely contact metadata. After the owner has created operational data, do not change it during routine rotation. A changed email causes the next successful login to upsert a different `User`; it does not transfer existing invitations or ownership. Recover an incorrectly configured email through a reviewed data-repair procedure rather than deleting users or changing ownership ad hoc.

`OWNER_NAME` may be changed and redeployed without changing the identity key. `OWNER_LOGIN_ID` can also be rotated independently of `OWNER_EMAIL`.

## Password hash format

The password generator and runtime verifier share the same canonical implementation. The stored format is self-describing:

```text
scrypt$v1$16384$8$1$64$<salt-base64url>$<derived-key-base64url>
```

Parameters are scrypt `N=16384`, `r=8`, `p=1`, a 64-byte derived key, and a random salt of at least 16 bytes. Passwords are not trimmed or normalized. The generator accepts 16 through 512 characters, reads the password from standard input, and rejects command-line password arguments. The verifier rejects malformed fields, unexpected or oversized parameters, invalid base64url, and wrong derived-key lengths before failing closed.

Credential comparison uses fixed-length digests and `timingSafeEqual`. Password verification still follows the dummy-hash path when the login ID is wrong or the stored configuration is unavailable, and a user is upserted only when both comparisons succeed.

## Generate an owner password hash on PowerShell

Use Node.js 20 and the checked-out repository. This example keeps the plaintext out of command history, passes it through standard input, and zeroes the unmanaged `SecureString` buffer in `finally`. The temporary managed string can only be cleared on a best-effort basis.

```powershell
$securePassword = Read-Host -AsSecureString 'New owner password'
$bstr = [Runtime.InteropServices.Marshal]::SecureStringToBSTR($securePassword)
$plainPassword = $null
try {
  $plainPassword = [Runtime.InteropServices.Marshal]::PtrToStringBSTR($bstr)
  $plainPassword | npm run --silent auth:hash
  if ($LASTEXITCODE -ne 0) { throw "Owner hash generation failed with exit code $LASTEXITCODE." }
}
finally {
  $plainPassword = $null
  [Runtime.InteropServices.Marshal]::ZeroFreeBSTR($bstr)
}
```

The command prints one hash line. Put that value directly into the environment's secret store as `OWNER_PASSWORD_HASH`. Do not paste the password or hash into chat, issues, commits, PR text, screenshots, shell scripts, or documentation. Do not create a local credential file.

Generate each unrelated secret separately:

```powershell
npm run --silent secret:generate # NEXTAUTH_SECRET
npm run --silent secret:generate # QUIZ_BADGE_SECRET
npm run --silent secret:generate # ADMIN_PASSPHRASE
```

Store each output immediately under its intended variable. Never reuse an output for another purpose.

## Rotation procedures

### Login ID

1. Choose a new non-public identifier that satisfies the documented length rules.
2. Update only `OWNER_LOGIN_ID` in the target environment's secret store.
3. Redeploy, verify protected readiness, then verify the new ID succeeds and the old ID fails.
4. Do not change `OWNER_EMAIL` as part of login-ID rotation.

### Password

1. Generate a new password hash through standard input using the procedure above.
2. Replace only `OWNER_PASSWORD_HASH` in the target environment's secret store.
3. Redeploy, verify protected readiness, then verify the old password fails and the new password succeeds.
4. Existing JWT sessions may remain valid. Rotate `NEXTAUTH_SECRET` only when invalidating every existing session is intentional.

### Security secrets

- Rotating `NEXTAUTH_SECRET` invalidates existing NextAuth JWT sessions and requires users to sign in again.
- Rotating `QUIZ_BADGE_SECRET` invalidates outstanding quiz badge tokens.
- Rotating `ADMIN_PASSPHRASE` requires readiness monitors and authorized admin callers to update their protected header value.

Redeploy after any environment-variable change and repeat the relevant readiness and authentication checks.

## Failure and recovery behavior

Wrong IDs, wrong passwords, malformed credentials, missing configuration, malformed hashes, and database failures all produce the same generic client-visible login failure. Detailed secret values, hashes, email values, connection strings, raw queries, and internal stack traces must never reach the client or logs.

Missing or invalid owner configuration fails closed. Do not restore access by adding a demo credential, hard-coded fallback, or previous public test account. For lockout recovery:

1. Confirm which configuration key is invalid without printing its value.
2. Generate a new owner hash or independent secret locally as required.
3. Replace the affected value through the approved environment secret store.
4. Redeploy and check protected readiness.
5. Verify authentication with the new credential and revoke or rotate any value suspected of exposure.

The previous public test-account authentication path has been removed. It must not be re-enabled as a rollback mechanism.
